# Фронтенд магазина

Каталог, корзина, оформление, оплата тестовой картой и наличными при получении.
Next.js 16 (App Router), TypeScript, TanStack Query.

Условия: [задание](../../docs/ASSIGNMENT.md) · [интеграция](../../docs/INTEGRATION.md) ·
[критерии](../../docs/EVALUATION.md).

## Запуск

Из корня репозитория, после `npm ci`, в двух терминалах:

```sh
npm run dev        # бэкенд, http://localhost:4000
npm run dev:web    # фронтенд, http://localhost:3000
```

Адрес API берётся из `NEXT_PUBLIC_API_URL`. Если бэкенд поднят на другом порту, скопируйте
`apps/web/.env.example` в `apps/web/.env.local` и поправьте значение.

```sh
npm run build:web       # сборка
npm run start:web       # запуск собранного
npm run typecheck:web   # tsc --noEmit
npm run test:web        # юнит-тесты (vitest)
npm run e2e:web         # сквозные сценарии (playwright)
```

Для e2e один раз нужен `npx playwright install chromium` — API и фронтенд Playwright поднимает
сам.

## Как устроено

Слои лежат в `src/`, зависимости направлены внутрь: `core → data → domain → features`.

```
core/      HttpClient, HttpError, Endpoint, журнал идемпотентности, хранилище;
           adapters/fetch — единственное место с fetch во всём приложении
data/      endpoints.ts — единственное место с URL; репозитории, dto/ собирает сущности
domain/    без React: entities/*.entity.ts (данные + правила) и *.service.ts
query/     кэш серверного состояния: <область>/*.queries.ts, ключи, клиент
features/  экраны: *.module.tsx + *.hooks.ts
providers/ сборка графа зависимостей, доступ к сервисам через useXxxService()
ui-kit/    Button, TextField, Fieldset, Alert, Modal, …
```

Поток данных: `страница → модуль фичи → *.hooks.ts → useXxxService() → доменный сервис →
репозиторий → HttpClient`. Компонент в сеть не ходит, заголовки не собирает и ошибки не
разбирает: готовый текст приходит из `getErrorMessage(error)`, ошибки полей уезжают в форму
через `applyFieldErrors`.

Обязанности разведены так, чтобы каждую можно было менять по отдельности:

| Что нужно изменить                      | Где                                                                            |
| --------------------------------------- | ------------------------------------------------------------------------------ |
| Добавить запрос к API                   | `data/endpoints.ts` → метод репозитория → хук в `query/<область>/*.queries.ts` |
| Заголовки, авторизация, повтор на `401` | `core/adapters/fetch/fetch.adapter.ts`                                         |
| Разбор ответа и конверта API            | там же, метод `_toResponse`                                                    |
| Разбор тела ошибки и ошибок полей       | `data/dto/api-response/api-error.dto.ts`                                       |
| Текст ошибки для пользователя           | `domain/errors/error-message.ts` — таблица кодов                               |
| Политика повторов запросов              | `query/query-client.ts`                                                        |
| Правило предметной области              | `domain/<область>/entities/*.entity.ts`                                        |

### Устойчивость

- **Идемпотентность.** Ключ хранится вместе с отпечатком тела запроса: повтор с тем же телом
  получает тот же ключ и второго заказа не создаёт. На конечном статусе оплаты ключ
  освобождается, поэтому «Оплатить снова» всегда создаёт новую попытку. Ключи выставляет
  репозиторий, компоненты о них не знают.
- **Сессия.** На `401` fetch-адаптер один раз пересоздаёт её и повторяет исходный запрос;
  параллельные запросы ждут один и тот же промис.
- **Перезагрузка.** Заказ и незавершённая оплата читаются с сервера по URL — хранить
  `paymentId` не нужно.
- **Конфликты.** Расчёт создаётся с версией корзины, прочитанной прямо перед запросом; при
  `CART_VERSION_CONFLICT` сервис повторяет попытку, при `QUOTE_EXPIRED` перечитывает расчёт,
  не стирая форму.
- **Опрос оплаты** идёт, только пока `paymentStatus = pending`; условие остановки — правило
  самого заказа, `order.isPaymentPending`.
- **Успех показывается по ответу сервера**, а не по факту удачной отправки запроса на оплату.

### Производительность

Агрегации по корзине — одним проходом: `cart.quantityIndex` и `Product.toStockIndex`
собирают `Map` через `reduce`, поэтому карточка каталога узнаёт своё количество за `O(1)`
вместо `find` по массиву на каждую карточку. Где нужно и отфильтровать, и преобразовать —
один `reduce` вместо `map().filter()`, который прошёл бы данные дважды и создал промежуточный
массив. Суммы всегда берутся из ответа API: считать деньги на клиенте — это второй источник
истины.

## Проверенные сценарии

`npm run e2e:web` — 14 сценариев в браузере, все проходят:

1. Оплата картой доходит до подтверждённого статуса заказа.
2. Отказ карты сохраняет заказ и допускает повторную оплату.
3. Отмена оплаты отличается от отказа и тоже допускает повтор.
4. Наличные завершаются оплатой при получении, без онлайн-оплаты.
5. Курьерская доставка добавляет стоимость доставки из API.
6. Пустую корзину нельзя оформить, товар без остатка не добавляется.
7. Двойное нажатие «Оформить» не создаёт второй заказ.
8. Перезагрузка во время ожидания оплаты доводит статус до результата.
9. Сбой сети при расчёте не стирает форму и предлагает пересчитать.
10. Потерянный ответ на создание заказа: повтор не создаёт второй заказ.
11. Сброшенный токен сессии восстанавливается автоматически.
12. Сценарий проходит без горизонтальной прокрутки при ширине 1280.
13. То же при ширине 390.
14. Форму можно заполнить и отправить с клавиатуры, диалог закрывается по Esc.

Сценарии 9 и 10 воспроизводят сбой перехватом запросов Playwright — в 10-м запрос доходит до
сервера, а ответ обрывается: ровно случай, когда заказ создан, а клиент об этом не узнал.

`npm run test:web` — 22 юнит-теста на домен: агрегации корзины и лимиты остатка, конечные
статусы оплаты, статусы заказа и право на повтор, описание доставки, разбор ошибки API, журнал
идемпотентности и условная валидация оформления.

## Принятые решения

- **Без UI-библиотеки.** Макета нет, вёрстка на SCSS-модулях. Значения темы — CSS-переменные
  в `app/globals.scss` (видны в девтулзах, меняются без пересборки), а брейкпоинты и миксины —
  SCSS в `styles/`, чтобы они не были рассыпаны по файлам.
- **Сущности вместо сырых ответов.** Ответ API не поднимается выше `data`: `dto/*.dto.ts`
  собирает из него сущность, и наверх едет уже она. Правило живёт рядом с данными, которых
  касается — `order.canPay`, `cart.quantityIndex`, `product.maxQuantity`, — поэтому экран
  спрашивает заказ о его состоянии, а не пересобирает условие у себя. Мелкие значения
  (`Customer`, `Delivery`, позиция корзины) остались типами из `@checkout/contracts`:
  поведения у них нет, а переписывать их вручную — двойная работа без выгоды.
- **`query/` — слой кэша, а не папка с хуками.** Корзину читают четыре места: шапка, каталог,
  корзина и оформление. При прямых вызовах сервисов это четыре запроса и четыре расходящиеся
  копии — счётчик в шапке не обновлялся бы после добавления товара из каталога.
- **Валидация — `react-hook-form` + `yup`.** Схема одна, повторяет серверные ограничения;
  условия описаны через `when` (самовывозу нужен пункт выдачи, курьеру — адрес). Та же схема
  доставки работает вне формы: пока адрес не дозаполнен, запрос за расчётом не уходит.
- **Расчёт доставки — `useQuery`, а не мутация.** Он однозначно определяется парой «версия
  корзины + доставка», поэтому ключ запроса сам пересоздаёт расчёт при любом изменении.
- **Диалог оплаты живёт на странице заказа**, а не на оформлении: так он переживает
  перезагрузку и остаётся единственным местом, где оплата запускается и повторяется. Сама
  модалка — нативный `<dialog>`, фокус-ловушка и Esc из коробки.

## Недоработки

- Нет истории заказов: заказ открывается по прямой ссылке после оформления.
- Расчёт обновляется по таймеру раз в 5 минут; отсчёта до истечения и предупреждения нет.
- Ошибка оплаты в диалоге не сбрасывается при повторном открытии.
- Нет тёмной темы и анимаций переходов между состояниями.
- Юнит-тестами покрыт домен, но не React-компоненты — на них смотрят сквозные тесты.
