# Фронтенд магазина — решение тестового задания

Каталог, корзина, оформление, тестовая оплата картой и наличными при получении.
Next.js 16 (App Router) + TypeScript, клиентский рендер, состояние сервера — TanStack Query.

Условия: [задание](../../docs/ASSIGNMENT.md) · [интеграция](../../docs/INTEGRATION.md) ·
[критерии](../../docs/EVALUATION.md).

## Запуск

Из корня репозитория, после `npm ci`:

```sh
npm run dev        # бэкенд на http://localhost:4000
npm run dev:web    # фронтенд на http://localhost:3000
```

Команды нужно держать в двух терминалах: `dev` поднимает API, `dev:web` — фронтенд.
Адрес API берётся из `NEXT_PUBLIC_API_URL`, по умолчанию `http://localhost:4000`.
Если API запущен на другом порту, скопируйте `apps/web/.env.example` в
`apps/web/.env.local` и поправьте значение.

Сборка и запуск собранного фронтенда:

```sh
npm run build:web
npm run start:web
```

Проверки:

```sh
npm run typecheck:web   # tsc --noEmit
npm run test:web        # юнит-тесты доменных правил (vitest)
npm run e2e:web         # сквозные сценарии в браузере (playwright)
```

Для `e2e:web` нужен `npx playwright install chromium` один раз. Playwright сам поднимет API и
фронтенд, если они ещё не запущены.

## Как устроено решение

Слои лежат в `src/`, зависимости направлены внутрь: `core → data → domain → features`.
Раскладка повторяет layered-архитектуру, которую я применяю на рабочем проекте, но без
DI-контейнера и без второго стора — на этом масштабе они не окупаются.

```
core/      инфраструктура, ничего не знает про магазин
  http/            HttpClient (интерфейс), HttpError, Endpoint
  adapters/fetch/  ЕДИНСТВЕННОЕ место с fetch во всём приложении
  idempotency/     журнал ключей идемпотентности
  storage/         интерфейс хранилища + адаптер localStorage
  form/            перенос серверных ошибок полей в react-hook-form
data/      доступ к API
  endpoints.ts     ЕДИНСТВЕННОЕ место, где живут URL
  repositories/    по репозиторию на область, метод = вызов API
  dto/             разбор конверта ошибки в HttpError
domain/    бизнес-правила без React
  <область>/*.rules.ts     чистые функции: статусы, лимиты, агрегации
  <область>/*.service.ts   оркестрация репозиториев
features/  экраны: *.module.tsx + *.hooks.ts
providers/ сборка графа зависимостей и доступ к сервисам через useXxxService()
query/     ключи, клиент, хуки запросов и мутаций
ui-kit/    Button, TextField, Fieldset, RadioOption, Alert, Modal, …
styles/    общие партиалы SCSS: брейкпоинты и миксины
```

Компонент — это папка со своим `index.ts`: наружу видно только то, что он реэкспортирует.
Переиспользуемые компоненты в `ui-kit` называются `<имя>.component.tsx`, экраны и их части
в `features` — `<имя>.module.tsx`, поэтому по имени файла сразу понятно, знает ли компонент
про данные. Стили лежат рядом в `<имя>.module.scss`. Корневой компонент фичи лежит в корне её
папки рядом с `*.hooks.ts`, вложенные части получают свои папки.

Поток данных: `страница → модуль фичи → *.hooks.ts (TanStack Query) → useXxxService() →
доменный сервис → репозиторий → HttpClient`. Компонент никогда не обращается к сети напрямую.

### Где что менять (критерий D2)

| Что нужно изменить                                                  | Файл                                                                                |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Добавить запрос к API                                               | метод в `data/repositories/<область>/*.repo.impl.ts` + строка в `data/endpoints.ts` |
| Общие заголовки, авторизация, таймауты                              | `core/adapters/fetch/fetch.adapter.ts`                                              |
| Разбор ответа, конверт `data/meta/links`, `Location`, `Retry-After` | `core/adapters/fetch/fetch.adapter.ts`, метод `_toResponse`                         |
| Перевод ошибки API в понятный текст                                 | `domain/errors/error-message.ts` (таблица кодов)                                    |
| Разбор тела ошибки и ошибок полей                                   | `data/dto/api-response/api-error.dto.ts`                                            |
| Политика повторов запросов                                          | `query/query-client.ts`                                                             |
| Правило предметной области (статусы, лимиты)                        | `domain/<область>/*.rules.ts`                                                       |

Ни один компонент не разбирает ошибки и не собирает заголовки: экран получает готовый текст
через `getErrorMessage(error)`, а ошибки полей уезжают в форму через `applyFieldErrors`.

### Что закрывает устойчивость

- **Идемпотентность.** `core/idempotency` хранит ключ вместе с отпечатком тела запроса.
  Повтор с тем же телом получает тот же ключ — сервер отвечает `200` с уже созданным заказом
  или попыткой, второй заказ не появляется. Изменилось тело — выдаётся новый ключ. Ключ попытки
  оплаты освобождается, когда попытка дошла до конечного статуса, поэтому «Оплатить снова»
  всегда создаёт новую попытку. Компоненты про ключи не знают, их выставляет репозиторий.
- **Восстановление сессии.** Токен лежит в `localStorage`. На `401` fetch-адаптер один раз
  пересоздаёт сессию и повторяет исходный запрос; параллельные запросы ждут один и тот же
  промис, поэтому лишних сессий не создаётся.
- **Перезагрузка страницы.** Страница заказа читает заказ с сервера по URL; незавершённую
  оплату находит через `GET /api/orders/{id}/payments`, сохранённый `paymentId` не нужен.
- **Конфликт версии корзины.** Расчёт всегда создаётся с версией, прочитанной непосредственно
  перед запросом; при `409 CART_VERSION_CONFLICT` `checkout.service` повторяет попытку с
  актуальной версией. При `QUOTE_EXPIRED` на оформлении расчёт и корзина перечитываются,
  введённые данные формы остаются на месте.
- **Опрос оплаты.** Опрашивается заказ, и только пока `paymentStatus = pending`. Условие
  остановки — доменное правило `getIsPaymentPending`; при уходе со страницы TanStack Query
  снимает подписку сам, устаревшие ответы отбрасываются им же.
- **Успех — только с сервера.** Страница успеха рисуется по `status`/`paymentStatus` заказа,
  а не по факту удачной отправки запроса на оплату.

### Производительность

Агрегации по позициям — одним проходом. `getQuantityIndex` и `getStockIndex` собирают
`Map` через `reduce`, поэтому карточка каталога узнаёт своё количество в корзине за `O(1)`
вместо `find` по массиву на каждую карточку: без индекса отрисовка каталога стоила бы
`O(товары × позиции)`.

Там, где нужно и отфильтровать, и преобразовать, это делается одним `reduce`, а не цепочкой
`map().filter()`: цепочка проходит данные дважды и создаёт промежуточный массив, который тут же
выбрасывается — лишняя аллокация и лишняя работа сборщику мусора. Одиночный `map` без фильтра
оставлен как есть: он и так один проход, а `reduce` вместо него только ухудшил бы читаемость.

Отображаемые суммы всегда берутся из ответа API и локально не пересчитываются: считать деньги
на клиенте — это второй источник истины, который рано или поздно разойдётся с сервером.

## Проверенные сценарии

Автоматически, `npm run e2e:web` — 14 сценариев, все проходят:

1. Оплата картой доходит до подтверждённого статуса заказа.
2. Отказ карты сохраняет заказ и допускает повторную оплату.
3. Отмена оплаты отличается от отказа и допускает повтор.
4. Наличные завершаются сообщением об оплате при получении, без онлайн-оплаты.
5. Курьерская доставка добавляет стоимость доставки из API (0 ₽ → 390 ₽).
6. Пустую корзину нельзя оформить, товар без остатка не добавляется.
7. Двойное нажатие «Оформить» не создаёт второй заказ (сверка через `GET /api/orders`).
8. Перезагрузка во время ожидания оплаты доводит статус до результата.
9. Сценарий проходит без горизонтальной прокрутки при ширине 1280.
10. То же при ширине 390.
11. Форму оформления можно заполнить и отправить с клавиатуры, диалог оплаты закрывается по Esc.
12. Сбой сети при расчёте доставки не стирает форму: показана ошибка и кнопка «Пересчитать»,
    после восстановления связи расчёт возвращается.
13. Потерянный ответ на создание заказа: повтор с тем же телом и ключом не создаёт второй
    заказ — проверяется через `GET /api/orders`.
14. Сброшенный токен сессии восстанавливается автоматически, приложение остаётся рабочим.

Сценарии 12 и 13 воспроизводят сбой через перехват запросов Playwright: 12-й обрывает
`POST /api/quotes`, 13-й пропускает запрос на сервер и обрывает ответ — ровно тот случай,
когда заказ уже создан, а клиент об этом не узнал.

Юнит-тесты, `npm run test:web` — 20 проверок: агрегации корзины и лимиты остатка, конечные
статусы оплаты, статусы заказа и право на повтор оплаты, разбор ошибки API с переводом
`body/customer/email` в `customer.email`, поведение журнала идемпотентности и условная
валидация оформления (самовывозу нужен пункт выдачи, курьеру — адрес).

## Осознанные решения

- **Макета нет**, интерфейс собран на SCSS-модулях без UI-библиотеки: меньше зависимостей и
  видно саму вёрстку. Значения темы остались CSS-переменными в `app/globals.scss` — они живут
  в рантайме, видны в девтулзах и позволяют менять тему без пересборки, в отличие от
  переменных SCSS. На SCSS вынесено то, что компилируется: брейкпоинты и миксины
  в `styles/`, чтобы `900px` и `560px` не были рассыпаны по файлам, а повторяющиеся блоки
  (`stack`, `loading-state`, `money-row`, `focus-ring`) описывались один раз.
- **Типы берутся из `@checkout/contracts`.** Отдельный слой сущностей и мапперов не заводил:
  на этом API он превратился бы в построчное переписывание готовых типов. Поведение вынесено
  в чистые функции `*.rules.ts`, поэтому данные в кэше TanStack Query остаются сериализуемыми.
- **Валидация — `react-hook-form` + `yup`.** Схема оформления одна, в
  `features/checkout/checkout.schema.ts`, и повторяет серверные ограничения. Условные правила
  описаны через `when`: самовывозу нужен пункт выдачи, курьеру — адрес, поэтому при самовывозе
  пустые поля адреса не подсвечиваются. Схема доставки переиспользуется и вне формы —
  `isValidSync` не пускает запрос за расчётом, пока адрес не дозаполнен. Ошибки полей от
  сервера приходят в ту же форму через `applyFieldErrors`, так что место показа ошибки одно.
- **Расчёт доставки — `useQuery`, а не мутация**, хотя под ним `POST /api/quotes`. Расчёт
  однозначно определяется парой «версия корзины + доставка», поэтому ключ запроса из этой пары
  сам пересоздаёт расчёт при любом изменении и даёт готовые состояния загрузки и ошибки.
- **Диалог оплаты живёт на странице заказа**, а не на оформлении: так он переживает
  перезагрузку и остаётся единственным местом, где запускается и повторяется оплата.
- **Нативный `<dialog>`** вместо своей модалки — фокус-ловушка и закрытие по Esc из коробки.
- `data-testid` есть только на трёх строках итогов: без них локаторы сумм в тестах ломались бы
  об одинаковые подписи цен.

## Известные недоработки

- Нет истории заказов: `GET /api/orders` используется только в тесте на двойное нажатие.
  Заказ открывается по прямой ссылке, полученной после оформления.
- Расчёт обновляется по таймеру раз в 5 минут, чтобы не протух за отведённые API 10 минут.
  Точного отсчёта до истечения и предупреждения пользователю нет.
- Ошибка оплаты в диалоге не сбрасывается при повторном открытии — сообщение остаётся до
  следующей попытки.
- Нет тёмной темы и анимаций переходов между состояниями.
- Юнит-тестами покрыт домен, но не React-компоненты: на компоненты смотрят сквозные тесты.

## Затраченное время

Около 4 часов: примерно час на слой интеграции (`core` + `data`), полтора часа на экраны,
45 минут на устойчивость и восстановление, полчаса на адаптив и доступность, остальное — тесты
и README.
